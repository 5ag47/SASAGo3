# 운영 백업과 복구 검증

운영 대상은 `wrangler.toml`의 `sasago3-game` 하나입니다. 백업·검증 도구는 원격 DB를 읽고, 복구는 메모리 임시 DB에서만 실행합니다. 운영 DB에 덮어쓰는 명령은 포함하지 않습니다.

## 백업 만들기

1. 이 저장소의 `package.json`이 있는 폴더에서 터미널을 엽니다.
2. `npm run cloud:backup`을 실행합니다. 기존 Wrangler 계정 연결과 `.local/cloudflare-player-secret`이 있어야 합니다. 키가 없다는 오류가 나오면 새 키를 만들지 말고 기존 운영 키의 보관 위치부터 확인합니다.
3. 종료 코드 0과 `integrity: "ok"`, `revisionCheck: true`를 확인합니다. 비어 있는 DB에는 revision 검사 대상이 없어 `null`이 표시됩니다.
4. 출력의 `archive` 경로가 암호화 백업입니다. 같은 경로 뒤에 `.report.json`이 붙은 파일에는 생성 시간·해시·건수·검사 결과만 있습니다.
5. 기존 백업 파일을 덮어쓰지 않습니다. 배포·스키마 변경 전마다 새 백업을 만들 수 있습니다. 자동 주기 실행을 설정한 것은 아닙니다.

도구는 Time Travel 북마크 조회 → SQL 내보내기 → AES-256-GCM 암호화 → 복호화 검증 → 메모리 DB 복원 → 무결성/저장 형식/revision 검사 순서로 실행합니다. 임시 SQL은 정상 종료·예외 처리 시 삭제합니다. 프로세스 강제 종료 때 남은 `.export-*.sql`은 개인정보가 든 임시 파일이므로 공개하거나 Git에 넣지 않습니다. 오류 출력은 단계·코드로 제한하며 SQL·닉네임·서명된 다운로드 주소·토큰은 출력하지 않습니다.

백업 암호화 키는 기존 운영 비밀값에서 HKDF로 별도 용도를 지정해 파생합니다. **암호화 백업과 기존 비밀값이 모두 있어야 복구를 검증할 수 있습니다.** 비밀값은 서버의 플레이어 식별에도 쓰이므로 임의로 재생성·교체하지 않습니다. 다른 기기에 보관할 때는 암호화 백업과 키를 분리해 본인만 접근 가능한 저장소에 보관하며 채팅·Git·게임 정적 파일로 공유하지 않습니다. 이 도구가 계정 외부의 안전한 장기 보관까지 자동으로 설정해 주지는 않습니다.

## 저장한 백업 다시 검사하기

1. 앞서 출력된 `archive`의 실제 경로를 찾습니다.
2. 아래 예시의 파일 이름 전체를 실제 파일 이름으로 바꾸고 따옴표 안에 넣습니다.

```sh
npm run cloud:backup -- --verify ".local/cloud-backups/실제-백업-파일이름.json"
```

3. `integrity: "ok"`와 검사 결과를 확인합니다. 이 명령은 원격 API를 호출하지 않으며 운영 DB를 변경하지 않습니다.
4. `BACKUP_AUTHENTICATION_FAILED`는 잘못된 키 또는 파일 손상, `BACKUP_WRONG_DATABASE`는 다른 DB의 사본, `BACKUP_STATE_INVALID`는 저장 형식·revision의 불일치를 뜻합니다. 파일 내용을 채팅에 붙이지 말고 오류 코드와 report 파일의 해시만 진단에 사용합니다.

## 실제 장애에서 운영 복구를 결정할 때

Cloudflare D1은 Time Travel 복구를 제공하며 현재 무료 플랜의 범위는 최근 7일입니다. 운영 복구는 현재 DB를 덮어쓰므로 장애 시점·복구할 시점·유실될 정상 플레이 범위를 확인한 뒤 별도로 결정해야 합니다. [Cloudflare 공식 Time Travel 문서](https://developers.cloudflare.com/d1/reference/time-travel/), [SQL 내보내기 명령](https://developers.cloudflare.com/d1/wrangler-commands/#d1-export)

1. 우선 현재 상태의 새 백업을 보존합니다. 오래된 백업을 덮어쓰지 않습니다.
2. 장애 발생 시간과 마지막 정상 저장 시간을 확인합니다. 서버 요청 trace·revision·오류 코드를 사용하고 플레이어 기록을 공개하지 않습니다.
3. 원하는 사본을 위 검증 명령으로 먼저 검사합니다.
4. 실제 운영 덮어쓰기는 이 도구로 자동 실행하지 않습니다. 점검 시간·대상 DB·복구 시점·유실 범위를 구체적으로 정한 복구 작업으로 진행합니다. 승인되지 않은 다른 DB나 기존 `sasago3-prod`·`sasago3-dev`는 대상이 아닙니다.
5. 실제 복구 후에는 본인 계정 로그인·일정 수정·새로고침 복구와 다른 계정의 기록 격리를 별도로 확인해야 합니다.

## 2026-10-27 실제 확인

2026.10.28-3 배포 직전 추가 사본: 플레이어1명·영수증58개, integrity:ok·revisionCheck:true·restoredToProduction:false. 암호화 사본은 `.local/cloud-backups/2026-10-28T00-36-43-651Z-e53fab53-62c4-4b00-94f2-b098d271968c.json`이며 Git에서 제외합니다. 실제 운영 DB는 덮어쓰지 않았습니다.

2026-10-28 추가 확인: 현재 운영 DB의 플레이어1개·영수증40개를 새 암호화 사본으로 보관했습니다. 최초 인증 오류 후 기존 OAuth 연결 상태를 확인하고 재시도해 성공했습니다. 무결성ok·revisionCheck:true·restoredToProduction:false이며 새 게임 흐름으로 저장 변환도 메모리 DB에서 검증했습니다.

운영 DB의 저장 1개·명령 영수증 3개를 암호화로 내보내고, 메모리 DB 복원·무결성·구버전 저장 변환·revision 일치·오래된 revision 갱신 거절을 통과했습니다. 저장한 암호화 파일을 다시 여는 독립 검증도 통과했습니다. 복구 드릴의 갱신은 메모리 DB에서 롤백했으며 `restoredToProduction: false`입니다. 이는 운영 DB 덮어쓰기 복구나 장기 장애 대응을 완료했다는 뜻은 아닙니다.
