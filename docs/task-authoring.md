# 과제·미니게임 모듈·그룹 편집

과제 내용은 `data/assignments.json`, 플레이 규칙은 `src/domain/task-modules`, 미니게임 화면은 `src/features/year-game/task-games`에 있습니다. 기존 과제 94개의 ID·일정·분량·효과를 옮겼으며 새 과제 내용을 추가하지 않았습니다. 과목별 평가 비율도 유지합니다.

## 로컬 편집기 사용

1. GitHub Desktop에서 SASAGo3 저장소를 선택하고 현재 브랜치가 `codex/sasago3-web-game`인지 확인합니다. 새 브랜치를 만들지 않습니다.
2. 이 프로젝트의 터미널에서 `npm run tasks:editor`를 실행합니다. 프로젝트 경로는 `C:\Users\retet\OneDrive\Documents\Github\unity-practice\unity-project\SASAGo3`입니다.
3. 브라우저에서 `http://127.0.0.1:5182/`를 엽니다. 공개 게임과 별도인 로컬 편집기입니다. 로그인이나 플레이어 저장 접근은 없습니다.
4. 위쪽 **과제·미니게임** 탭을 선택합니다. 왼쪽에서 기존 과제를 선택하면 이름·설명·과목·일정·분량·단계·완료/미완료 효과를 바꿀 수 있습니다. 기존 ID는 바꾸지 않습니다. 옆 **학사 달력** 탭은 [날짜 편집](calendar-authoring.md)용입니다.
5. 새 과제가 필요하면 ‘새 과제·그룹 ID’에 영문 ID를 입력하고 ‘빈 과제 만들기’를 누릅니다. 이름과 내용을 직접 입력합니다. 이 작업만으로 게임 파일이 바뀌지는 않습니다.
6. ‘처리 모듈’에서 순서 정리(order_v2) 또는 패턴 기억(pattern_v2)을 선택합니다. 비워 두면 그룹 설정을 따릅니다. 과목 과제의 기본값은 순서 정리, 공통 과제는 패턴 기억입니다. 첫 주 수학 실습은 수학 공부를 실제 실행하면 자동 완료하는 시간 과제입니다.
7. 여러 과제를 묶으려면 ‘그룹 만들기’를 누르고 그룹 이름·모듈을 정한 뒤 묶을 과제를 체크합니다. 과제에 직접 지정한 모듈이 그룹보다 우선합니다. 서로 다른 그룹의 모듈 설정이 충돌하면 입력 문제로 표시합니다.
8. 입력 문제가 0개가 되면 ‘변경 N개 내보내기’를 누릅니다. 다운로드 폴더에 `sasago3-task-changes.json`이 생깁니다. 과제 목록 전체가 아니라 변경한 항목과 편집 전 값만 포함합니다.
9. 터미널에서 아래 명령을 실행합니다. 파일을 다른 위치에 받았다면 따옴표 안의 경로만 실제 위치로 바꿉니다.

```powershell
npm run tasks:apply -- "C:\Users\retet\Downloads\sasago3-task-changes.json"
npm run check
npm test
```

10. 성공하면 GitHub Desktop의 Changes에서 `data/assignments.json`의 변경을 확인합니다. 공개 게임 반영은 보안 빌드와 배포가 필요하며 로컬 편집만으로 공개 서버가 바뀌지 않습니다.

다른 사람이 다른 과제를 수정했다면 그 내용을 보존하고 합칩니다. 같은 항목이 편집 전 값과 다르면 해당 ID를 표시하고 전체 적용을 중단합니다. 최신 내용을 다시 연 뒤 자신의 변경을 비교해 적용하세요. 강제 덮어쓰기는 없습니다. 적용 전 파일은 `.local/task-edit-backups`에 백업합니다. 적용 작업끼리는 잠금 파일로 직렬화합니다. 외부 편집기와 Git의 모든 동시 변경까지 방지한다고 보장하지는 않습니다.

공통 항목 비교와 파일 적용은 달력 편집과 공유하며 검증기는 형식별로 분리되어 있습니다. 전체 개발 검사는 `npm run verify`로 실행할 수 있습니다. 과제의 조건부 발생은 `when`·`chance`로 확장합니다. [확장 안내](gameplay-extension.md)를 참고합니다.

자소서의 개별 모듈에는 `params.support: "essay"`를 지정했습니다. 그룹보다 개별 지정이 우선하므로 일반 패턴 기억 그룹을 바꿔도 자소서 보조 모델이 사라지지 않습니다. 새 모듈이 이 보조를 쓸 때는 호스트 문맥의 `support(model, quality)`와 `supportCost(model, effects)`를 사용합니다. `support: "none"`은 명시적으로 보조를 끕니다. 같은 비용·품질 공식을 화면에 복제하지 않습니다. 과제 완료 주는 `completedWeek`에 기록합니다.

## 실제 플레이 흐름

- 할 일을 자습시간에 넣고 한 주를 진행합니다. 배정한 시간에 실행이 멈추면 ‘작업 시작’을 누릅니다. 순서 정리는 네 숫자를 오름차순으로, 패턴 기억은 기억한 네 칸을 고릅니다. 제한 시간은 없습니다.
- 도전 시작 때 비용을 한 번 소비합니다. 중간 저장 후 재개는 같은 도전이며 비용을 다시 내지 않습니다. 명시적 재도전·중단 후 새 작업에는 새 비용과 횟수를 적용합니다.
- 성공 직후 그 시간의 작업량과 품질을 반영합니다. 전체 분량이 채워지면 그 자리에서 완료합니다. 완료한 뒤 다시 시간을 배정하거나 주가 끝날 때까지 기다릴 필요가 없습니다.
- 장기 과제는 배정한 칸마다 여러 회차를 진행합니다. 한 주 여러 번 가능하고 주간 상한은 별도 설정입니다. 상한을 소진한 이후 배정은 휴식으로 바뀌고 이유를 기록합니다.
- 일반 선택은 즉시 화면에 반영하고 짧은 묶음으로 서버에 저장합니다. 결과·품질·진척은 서버가 검증한 응답으로 확정합니다. 임시 입력은 탭의 sessionStorage에 남아 재접속 때 저장 순서와 대조합니다. 충돌은 자동 덮어쓰지 않습니다.
- 반복 과제는 각 발생 주별로 별도 ID·보드·도전 기록을 가집니다. 단계는 전체 진척도를 나누며 전체 완료 효과는 한 번만 적용합니다. 현금 보상은 없습니다.

## 회차·비용 설정

편집기에서 과제 또는 그룹을 선택하고 모듈을 v2로 정합니다. ‘주간 도전 상한’을 비워 두면 횟수 제한이 없으며, 실제로는 배정한 시간 안에서 진행합니다. 숫자를 넣으면 과제별 그 주의 시작·재도전 합계에 상한을 적용합니다. 여러 과제가 같은 그룹을 써도 횟수는 합산하지 않습니다.

설정 JSON의 예시는 다음과 같습니다. 필요한 항목만 지정하면 나머지는 기본값을 따릅니다.

```json
{
  "cost": { "hp": -0.5, "focus": -0.25, "stress": 1 },
  "mistake": { "stress": 0.5 },
  "success": {},
  "failure": { "stress": 2 },
  "weeklyLimit": null,
  "overloadAfter": 2,
  "overloadHealth": 0.75,
  "overloadStress": 1.5,
  "variance": 0,
  "earlyWeeks": 4,
  "earlyQuality": 90,
  "earlyEffect": { "science": 0.75, "focus": 0.25 }
}
```

위 설정의 3번째 도전은 기본 비용에 체력 -0.75·스트레스 +1.5, 4번째는 -1.5·+3을 더합니다. 비용뿐 아니라 자습 활동 자체의 부담도 적용합니다. 체력 30 미만·스트레스 70 이상은 각각 작업 품질 -10이며 주중 극심한 무리는 주말에 회복해도 다음 주 피로를 남깁니다. 시작 4주 안에 품질 90 이상이면 지정한 능력 보너스를 받습니다. 졸업논문에 이 초반 보너스를 적용했습니다.

variance는 서버 시드로 정하는 품질 가감 범위(0~10)입니다. 공통 스탯은 hp·focus·stress·math·science·writing·speech·reputation·charm입니다. 각 효과는 -30~30 범위로 검사합니다. 예시 두 모듈의 실수는 그 회차를 계속할 수 있고 mistake 효과를 적용합니다. 별도 실패가 있는 모듈은 아래 status 계약을 구현합니다.

## 코드로 새 모듈 추가

1. `src/domain/task-modules/session-v2.js`와 order-v1/pattern-v1의 보드 계약을 참고해 새 파일을 만듭니다. 파일과 모듈 ID에 새 이름·버전을 붙입니다. 기존 버전을 삭제하지 않습니다.
2. 같은 화면을 재사용할 수도 있고 새 화면을 만들 수도 있습니다. 새 화면이면 `src/features/year-game/task-games`에 React 파일을 만들고 `registry.jsx` 및 `catalog.js`에 화면 ID를 등록합니다.
3. 도메인 모듈을 `src/domain/task-modules/registry.js`의 작은 등록 목록에 추가합니다. 중복 ID와 빠진 필수 함수를 검사합니다.
4. 편집기를 다시 열면 등록한 미니게임 모듈을 선택할 수 있습니다. 특정 과제에만 지정하거나 그룹에 연결합니다.
5. 새 모듈의 성공·실패·중간 저장·잘못된 입력·재전송 사례를 테스트하고 검사·빌드를 실행합니다.

게임 데이터에는 실행 코드나 파일 경로를 넣지 않습니다. 등록된 모듈 ID와 설정만 사용합니다. 모듈 코드는 개발자가 저장소에 추가하고 검토·배포합니다. 웹 플레이어가 보낸 JavaScript나 점수를 실행·신뢰하지 않습니다.

## 모듈 계약

| 함수/필드                              | 책임                                                                |
| -------------------------------------- | ------------------------------------------------------------------- |
| `id`, `name`, `unit`, `estimated`      | 버전이 있는 ID, 표시 이름, 진척 단위, 시간 추정 여부                |
| `validate(params)`                     | 설정 오류 문자열 배열. 정상은 빈 배열                               |
| `work(context)`                        | 시간 투자 시 진척 증가량과 선택적 `data` 반환                       |
| `isComplete(context)`                  | 완료 조건. 시간 처리와 미니게임 행동 후 공통으로 검사               |
| `estimate(context)`                    | 남은 예상 자습 칸 수. 프리셋과 주간 검토에서 공유                   |
| `complete(context)`, `expire(context)` | 점수 또는 null, 능력치 효과, 선택적 결과 메모·수상 횟수 반환        |
| `game.view`, `game.instructions`       | 화면 등록 ID와 시작 안내                                            |
| `game.create(context)`                 | 최초 미니게임 상태 생성                                             |
| `game.act(context, data, action)`      | 행동 검증 후 새 상태 반환                                           |
| `game.valid(data)`                     | 저장·복구 상태 검사                                                 |
| `game.public(data)`                    | 클라이언트에 보여 줄 상태. 패턴 정답은 입력 단계에서 숨김           |
| `attemptEffects(context)`              | 새 도전의 능력치 비용. 재개 때는 호출하지 않음                      |
| `actionEffects(context,before,after)`  | 행동·실수의 능력치 변화                                             |
| `finishAttempt(context)`               | quality(0~100), effects, 선택적 early 반환                          |
| `failAttempt(context)`                 | 선택적 실패 효과. 생략하면 스트레스 +2                              |
| `game.status(data)`                    | 선택적 playing/success/failure 판정. 생략하면 passed 사용           |
| `game.preview(data,action)`            | 선택적 화면 미리보기. {data,barrier} 또는 null. 난수·진척 확정 금지 |

`context`는 과제 스냅샷, 능력치, 모듈 설정, 과목 실력, 저장 난수를 사용하는 `roll()` 등을 제공합니다. 원본 상태를 직접 고치지 않고 결과를 반환합니다. 미니게임 상태는 과제의 `moduleData`에 저장하며 JSON 값, 깊이·항목 수·문자열 길이를 제한합니다. 두 예시는 `passed`로 통과 여부, `phase`로 진행 단계, `quality`로 결과 점수를 표시합니다.

공통 처리기가 진척도·결과 범위를 검사하고 능력치·성적·저장을 적용합니다. 개발자는 새 모듈에서 완료 조건과 채점·효과를 바꿀 수 있습니다. 미니게임 자체로 완료하는 모듈은 `isComplete`에 해당 조건을 정의하면 공통 완료 경로를 사용합니다. 한 모듈의 코드를 여러 과제가 공유해도 상태는 `task.id`별로 분리됩니다.

그룹과 설정은 과제 발생 시 스냅샷으로 저장합니다. 이후 설정 변경은 새로 발생하는 과제에 적용합니다. v1의 미완료 보드는 보존해 v2로 옮기며, 이전 방식에서 이미 검증된 통과 보드는 한 번만 완료로 전환합니다. 확정된 성적은 재계산하지 않습니다. time_v1·contest_v1과 두 v1 보드 처리기는 이전 저장 호환을 위해 남깁니다.

코드 모듈은 roll()로 무작위 보드·효과를 만들 수 있습니다. 비용 미리보기는 실제 시드를 소비하지 않으며 임의의 난수 비용은 추정값입니다. game.create/act는 새 상태를 반환하고 game.public은 정답 등 숨길 정보를 제거합니다. moduleData와 attempts를 함께 저장하므로 서버의 중복 요청은 비용이나 보상을 두 번 적용하지 않습니다.
